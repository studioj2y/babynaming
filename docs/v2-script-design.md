# 星命观测局 2.0 · 场景剧本与架构设计（定稿 v0.1）

> 基线：v1.0（tag `v1.0` → commit `0f138ee`）。2.0 **前端全重做，后端 `core.py` / `ai.py` 零改动复用**。
> 形态：视觉小说式（galgame）场景引导 —— 一屏一问、立绘登场、滑动淡入翻页、分支剧情。

## 一、已锁定的设计决策

| # | 决策 | 说明 |
|---|---|---|
| 1 | **一次只问一个问题** | 每幕一个提问（同一槽位的紧密字段可同屏，如父姓+母姓） |
| 2 | **翻页 = 滑动淡入** | 统一转场，不做 3D 翻卡/页卷曲。低端机稳、可降级 |
| 3 | **12 位老师是独立角色** | 各有立绘、各管一个专业节点，不是统称 |
| 4 | **星师是独立角色** | 压轴。揭晓时落笔，并负责结果页「星师详解」（= 现有 AI 解读） |
| 5 | **提问顺序沿用 v1.0** | 按 v1.0 表单顺序拆细为逐幕，保证与引擎数据依赖一致 |
| 6 | **收集完 → 汇总确认页** | 逐项可改。**不做「上一问回退」**（状态机可逆 + 对白重播成本高） |
| 7 | **占算是纯表演** | 立绘先后淡入淡出 + 复用 v1.0 互动文本（SOLO / BANTER） |
| 8 | **表演结束需点击才揭晓** | 关键戏剧张力点。此时两侧老师立绘齐聚，静待落笔 |
| 9 | **揭晓有动效与光效** | 星师落笔 → 光效 → 名单浮现 |
| 10 | **结果视觉：木牌质感** | 桌上木牌排列（细节待定） |
| 11 | 新名主人固定称谓 | **小星主** |
| 12 | AI 为可选增强层 | 模板驱动即可跑完全程；LLM 失效不影响主流程 |

## 三、「五师拉票」——v1.0 拖拽排序的场景化改造

v1.0 第二步是 6 维触屏拖拽排序（`weights`），与「一次只问一个问题」的轻量感冲突。

**改造方案**：五位维度老师**同屏登场自荐拉票**，请小星主「择其二」。

- 出场：意境（字义寓意）、音律（音律朗朗）、五行（五行调和）、生肖（生肖相宜）、字形（字形匀称）
- 交互：点选最看重的 2 位 → 映射为该 2 维权重上调
- **无生辰时生肖老师不参演**（直接复用 v1.0 已固化逻辑：`ORDER_DEF.filter(zodiac || hasBirth)`）
- 拖拽精细排序**移到结果页作为高级选项**保留，不进主流程

收益：把枯燥的权重排序变成有戏的「择师」，且天然符合世界观。

## 五、关键架构收益：表演与请求解耦

**占算表演期间并行发起 API 请求**，用户点击「揭晓」时数据已就位。

- 正常情况：零等待，点击即揭晓
- API 慢：表演自然延长（多播一段 BANTER），用户感知为「老师们还在推敲」
- API 失败：星师致歉退场 + 重试入口，不会白屏

即**把技术等待包装成戏剧张力**。这是幕 16「需点击才揭晓」带来的真实工程红利，不只是体验设计。

## 六、数据结构：剧本即数据

```
script.json
├─ characters: { 立绘路径, 默认位置, 名号, 称谓 }
├─ scenes: [
│    { id, type: 'brand'|'talk'|'ask'|'summary'|'ritual'|'reveal'|'result',
│      actor, enter/exit, lines: [多套台词随机池],
│      ask: { field, widget: 'text'|'seg'|'chips'|'date'|'pick2', validate },
│      next: sceneId | { branch: {...} } }
│  ]
└─ transitions: { 统一缓动与时长 }
```

一个 `director.js` 消费 `script.json` 驱动全流程。**加老师、加问题 = 改 JSON，不动代码。**
（v1.0 流程写死在 `index.html` 里，可维护性差一个量级。）

## 七、动效规范

| 场景 | 做法 | 时长 |
|---|---|---|
| 翻页转场 | 滑动淡入（`translateX` + `opacity`） | 320–360ms |
| 立绘登场 | 淡入 + 轻微上浮 / 缩放 | 400ms |
| 立绘退场 | 淡出 + 反向轻移 | 300ms |
| 占算轮替 | 立绘交叉淡入淡出，配文本逐条浮现 | 每位 1.2–1.8s |
| 主题色切换 | CSS 变量过渡，无闪烁 | 500ms |
| 揭晓光效 | 落笔 → 光晕扩散 → 木牌逐张浮现（错峰 80ms） | 1.2s |

- 统一缓动曲线（建议 `cubic-bezier(.22,.61,.36,1)`）
- 全程尊重 `prefers-reduced-motion`：降级为纯淡入

## 十三、部署与版本路由（路径共存方案）

**目标**：同一 Vercel 部署同时承载 v1 与 v2，可任意切换，互不破坏。

| 阶段 | 根路径 `/` | `/v1` | `/v2` |
|---|---|---|---|
| 调试期 | v1（原样不动） | （可不加，或指 v1） | **v2 预览** |
| 上线后 | **v2** | v1（回退入口） | （可重定向到 `/`） |

### 1. 目录结构（两个阶段的文件布局）

```
/                          # 根：调试期=v1 的 index.html；上线后=v2 的 index.html
  index.html
  api/                     # 共享 serverless 函数（generate / analyze / interpret ...）
    generate.py
    ...
  core.py  ai.py           # 引擎（v2 只读复用，不破坏 v1 行为）
  characters/  manifest.json
/v1/                       # 上线后才需要：把原 v1 静态前端搬进来
  index.html
/v2/                       # v2 前端（调试期在此，上线后上移根目录）
  index.html
```

### 2. `vercel.json` 重写规则

**调试期**（根=v1，`/v2`=v2）：

```json
{
  "rewrites": [
    { "source": "/v2", "destination": "/v2/index.html" },
    { "source": "/v2/(.*)", "destination": "/v2/$1" }
  ]
}
```
（根 `/` 与 `/api/*` 由 Vercel 默认规则正常服务 v1，无需额外写。）

**上线后**（根=v2，`/v1`=v1）：把 v1 的 `index.html` 移入 `/v1/`，v2 的 `index.html` 上移根目录，重写改为：

```json
{
  "rewrites": [
    { "source": "/v1", "destination": "/v1/index.html" },
    { "source": "/v1/(.*)", "destination": "/v1/$1" }
  ]
}
```
（`/v2` 此时已无意义，可在上线前删掉或加一条 `{ "source": "/v2", "destination": "/index.html" }` 重定向到根。）

### 3. 两个硬性前提（务必满足，否则路径切换会 404）

- **v2 前端资源必须用相对路径**：`index.html` 里引用 JS/CSS/图片用 `./assets/x.js`、`characters/...` 而非 `/assets/x.js`。这样同一份 v2 代码在 `/v2/`（资源解析为 `/v2/assets/...`）和根 `/`（解析为 `/assets/...`）下都能正确加载，上线搬家零改动。
- **API 走绝对路径 `/api/*`**：v2 调 `fetch('/api/generate')`（绝对），不依赖挂载点，在 `/v2` 和 `/` 下都打到根目录的共享函数。v2 新增端点（如 `/api/v2_chat`）也放根 `api/`，不进 `/v2/api/`，避免路由分裂。

### 4. 保证 v1「不受影响」的关键约束

- **调试期内不修改 v1 依赖的共享文件**：即根 `index.html`、`api/*.py`（已有）、`core.py`、`ai.py` 的行为保持不变。v2 的全部新代码放新文件（`/v2/index.html`、`api/v2_*.py`、必要时 `core_v2.py` 引擎副本）。
- 若 2.0 需要改引擎逻辑且会影响 v1 输出，必须**另起 `core_v2.py` 副本**给 v2 用，而非改 `core.py`；v1 的 `api/generate.py` 继续引 `core.py`。
- 如此，调试期 `/` 提供的 v1 与上线前完全一致；上线只是「文件搬家 + 改 vercel.json」，无代码重写。

### 5. 上线切换步骤（在你本机 git 完成）

1. 将当前根 `index.html`（v1）移到 `/v1/index.html`
2. 将 `/v2/index.html`（v2）上移到根 `index.html`
3. 更新 `vercel.json` 为上线后版本
4. 提交推送，Vercel 自动重部署
5. ⚠️ 用户浏览器可能缓存旧根 `/`（v1 的 index.html），上线后建议加缓存指纹或提示硬刷新（`Ctrl/Cmd+Shift+R`）

### 6. 替代思路（仅供参考，非采用）

Vercel 还支持「分支预览部署」：每个 git 分支自动获得 `*.vercel.app` 预览 URL（如 `dev-2-0-*.vercel.app`）。但用户明确要**路径共存**（`/v2`、`/v1`），故采用上方文件夹 + `vercel.json` 重写方案，而非分支预览。
